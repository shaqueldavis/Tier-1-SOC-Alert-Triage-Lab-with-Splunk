# Establish Scope

Now that we have verified the alert, let's establish the scope by continuing to investigate and answer various questions.

We already know:
- Detection: `Repeat Failed Login Attempts`
- Time: `2026-08-26 15:05:00 UTC`
- Severity: `Medium`
- Host source: `Splunk_Lab`
- failed logins: `5`
- Event ID: `4625`
- Log source type: `XmlWinEventLog:Security`

What we want to know:
- Targeted account
- Authentication source
- Logon type
- Failure reason
- Successful Authentication (event ID 4624)

## Targeted account

Determine which account was being targeted. Start with:
```spl
index=* host="<WINDOWS-HOSTNAME>" "<EventID>4625</EventID>"
| rex field=_raw "Name='TargetUserName'>(?<Target_User_Name>[^<]+)"
| rex field=_raw "Name='TargetUserSid'>(?<Target_User_Sid>[^<]+)"
| table _time Target_User_Name Target_User_Sid
```
in my case:
```
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| rex field=_raw "Name='TargetUserName'>(?<Target_User_Name>[^<]+)"
| rex field=_raw "Name='TargetUserSid'>(?<Target_User_Sid>[^<]+)"
| table _time Target_User_Name Target_User_Sid
```

We see each of the 5 failed login attempts but nothing was recorded for the field `TargetUserName`.

However, the field `TargetUserSid` did record `S-1-0-0` for all 5 events. S-1-0-0 is the Nobody/Null SID. In other words, Windows didn't successfully resolve the authentication attempt to an account identity when it generated this particular 4625 event.

This may not be the exact information we were looking for but it is information. 

We can now conclude:
- Targeted account: `The Windows 4625 events did not record a target username for these failed authentication attempts. TargetUserName was - and TargetUserSid was S-1-0-0.`

## Authentication source



Now determine where the authentication attempts originated. This is different from the host source. the host source tells us which machine generated the alert. the authentication source tells where the authentication attempt came from.


```spl
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| rex field=_raw "Name='IpAddress'>(?<IP_Address>[^<]+)"
| table _time IP_Address
```

The rex field is is telling Splunk to Search the raw XML for Name='IpAddress'>, then capture everything until the next < and put it into a new field called IpAddress.

This is because Splunk is not automatically extracting a field called `IpAddress`. So, we are essentially forcing it to do so. In the real world Splunk would be fully configured to extract these fields in a simpilar way. However, that configuration goes beyond the focus of this lab. So, we are using rex fields.

This is sometimes quicker than building unique rex SPLs.

## Logon type

Determine the Logon Type. This is one of the most important pieces of the investigation.

Common values include:

|---|---|
| 2	| Interactive	|
| 3	| Network	|
| 4	| Batch	|
| 5	| Service	|
| 7	| Unlock	|
| 8	| NetworkCleartext	|
| 9	| NewCredentials	|
| 10	| RemoteInteractive / RDP |
| 11	| CachedInteractive	|

index=* host="Splunk_Lab" "<EventID>4625</EventID>"

## Failure reason

Search for the failure reason

```spl
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| rex field=_raw "Name='FailureReason'>(?<Failure_Reason>[^<]+)"
| table _time Failure_Reason
```

We see `%%2304` for all 5 events. This is an index code that points to a text string within a local dll file. The associated text string is "An Error occurred during Logon". <br>
I know because I can access the effected host (my Windows VM) search for the event in Event Viewer, and open up the details that list the exact string along with the index code. 

<img width="1512" height="840" alt="image" src="https://github.com/user-attachments/assets/82c47c4b-c4f5-45da-b62b-fbf0274aa86e" />

<br>

<br>

In the real world, a SOC would not likely have access to the multitude of endpoints that generate alerts on their dashboard. Neither would they have to rely on common knowldge to determine what the code means. <br>
They would most likely rely on SIEM field enrichment (the production standard). In an enterprise environment, raw logs are enriched before or during ingestion. The Splunk Add-on for Microsoft Windows (Splunk_TA_windows) automatically maps FailureReason codes like %%2304 to human-readable text via pre-built lookup tables. <br> 
However, that is not something we will explore in this lab for the sake of simplicity and focus. <br>
They may also rely on an internal knowledge base such as runbooks. SOC teams maintain internal documentation repositories (such as Confluence or internal SIEM wikis). Common codes like `%%2304` are documented in standardized triage playbooks so analysts can reference them instantly.

The point is, don't be confused by `%%2304`, or how to figure out what it means. just know that in our case it means "An Error occurred during Logon".

This is a very high-level message that doesn't give us much detail, but it is additional context.

In addition to the failure reason two relevant codes that could provide us with more context would be the Status and sub SubStatus.

Modify the SPL to include Status and SubStatus:
```spl
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| rex field=_raw "Name='FailureReason'>(?<Failure_Reason>[^<]+)"
| rex field=_raw "Name='Status'>(?<Status>[^<]+)"
| rex field=_raw "Name='SubStatus'>(?<SubStatus>[^<]+)"
| table _time Status SubStatus Failure_Reason
```

<img width="2470" height="1238" alt="image" src="https://github.com/user-attachments/assets/500f3281-e13b-4c4d-b3b8-26affbf5c074" />

<br>

<br>
<br>

The status is `0xc000006d` and the Substatus is `0xc0000380`. These codes point to:
- `0xc000006d` = STATUS_LOGON_FAILURE / The attempted logon is invalid. This is either due to a bad username or authentication information.
- `0xc0000380` = STATUS_SMARTCARD_WRONG_PIN / An incorrect PIN was presented to the smart card.

The information behind these codes can be found here: <br>
<a href="https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55"><img src="https://img.shields.io/badge/-Microsoft_learn-0072b1?&style=for-the-badge&logo=Microsoft&logoColor=white" /></a>

<br>
<br>
<br>
<br>

Now we know that the login attempts failed because we entered bad "authentication information". That is consistent with the Status code. However, we also know that there was no "smartcard" involved in the process. That's inconsistent with the SubStatus code.

That said, machines are not perfect. If they were we would not need analysts. The exact resone behind why this status code is attached to this alert would require additional investigation. 

In the real world, a SOC analyst would not know whether or not a smart card was used, because they would not have engineered the detection the way we did in this lab. They would have to use the information from the alert along with other resources to make that determination.

The key thing to keep in mind as we perform investigation and triage is the word triage. Triage is essentially the process of sorting by the urgency of needs to make the best use of limited resources. That is relevant here because realistically it is not the job of a SOC analyst to travel down a rabbit hole and determine the reason behind every piece of telemetry. It is the SOC's job to document and interpret the telemetry to reach a supported conclusion.

In our case determining if a smart card was used or not isn't a priority, it is merely additional context. The important distinction here is to look at this information to conclude that "The SubStatus code for the alert is STATUS_SMARTCARD_WRONG_PIN", not "a smart card was used in the login attempt".  
  
Now we can conclude: 
- Failure reason: An Error occurred during Logon
- Status: `0xc000006d` = STATUS_LOGON_FAILURE / The attempted logon is invalid. This is either due to a bad username or authentication information.
- SubStatus `0xc0000380` = STATUS_SMARTCARD_WRONG_PIN / An incorrect PIN was presented to the smart card.

## Related Activity / Successful Authentication (event ID 4624)

This is one of the most important Tier-1 checks. We want to know was there ever a successful authenticate on this host? Because the failed login attempts did not record a targeted user, we will look for any successful attempts on the host in general following the time frame of the alert.

The time of the triggered alert was `2026-08-26 15:05:00 UTC`. So, we want to search for successful login during or shortly after the time.

change the filter time frame to `2026-08-26 15:00:00 UTC` through `2026-08-26 15:30:00 UTC`.

Seeing these accounts in the 4624 events is normal system telemetry mixed with user authentication activity. Either way, searching through 95 results is impractical so we want to narrow down our results with information that we have already uncovered.

We need to correlate the failed 4625 events with subsequent 4624 events. There are several pieces of evidence we can compare. `TargetUserName` and `TargetUserSid` won't provide any correlation for us because no account was recorded for our failed logins. So, we want to move to `LogonType` and `IpAddress`.

`127.0.0.1` is the loopback address, meaning the authentication originated locally on Splunk_Lab, rather than from another machine over the network. `LogonType` 2 is important because we're specifically interested in whether someone subsequently logged onto the Windows machine interactively.  

Search for successful logins where the `IpAddress` is `127.0.0.1` and the `LogonType` is `2`. include the `TargetUserName` and `TargetUserSid` to see the associated information:

```testing this spl
index=* host="Splunk_Lab" "<EventID>4624</EventID>"
| rex field=_raw "Name='TargetUserName'>(?<Target_User_Name>[^<]+)"
| rex field=_raw "Name='TargetUserSid'>(?<Target_User_Sid>[^<]+)"
| rex field=_raw "Name='LogonType'>(?<Logon_Type>[^<]+)"
| rex field=_raw "Name='IpAddress'>(?<Source_IP>[^<]+)"
| where Logon_Type="2" OR Source_IP="127.0.0.1"
| table _time Target_User_Name Target_User_Sid Logon_Type Source_IP
| sort _time
```

Notice how I use `0R` instead of `AND`. If we were to use `AND` we only get back results where the conditions are a match for both. By using `OR` we get back results were the conditions are a match for either or.

<img width="2480" height="1228" alt="image" src="https://github.com/user-attachments/assets/76052710-56f6-4126-b0b7-36d4904a5053" />

<br>

We have narrowed our search down to 8 results. UMFD-0 and UMFD-1	likely represent Windows User-Mode Font Driver accounts. DWM-1 likely represents Desktop Window Manager account. These are not normal human user accounts. In other words, these more closely signify normal windows activity opposed to an authorized person gaining access to our host.

The more interesting results are those with the `TargetUserName` of `simplesmartcyber@gmail.com`. 

A Logon Type 11 means Windows classified the logon as a cached interactive logon. A common example is a domain user's interactive login being authenticated with cached credentials rather than contacting the domain controller. To check and see if this is supported, add the `TargetDomainName` to our spl

```spl
index=* host="Splunk_Lab" "<EventID>4624</EventID>"
| rex field=_raw "Name='TargetUserName'>(?<Target_User_Name>[^<]+)"
| rex field=_raw "Name='TargetUserSid'>(?<Target_User_Sid>[^<]+)"
| rex field=_raw "Name='LogonType'>(?<Logon_Type>[^<]+)"
| rex field=_raw "Name='IpAddress'>(?<Source_IP>[^<]+)"
| rex field=_raw "Name='TargetDomainName'>(?<Target_Domain_Name>[^<]+)"

| where Logon_Type="2" OR Source_IP="127.0.0.1"
| table _time Target_User_Name Target_User_Sid Logon_Type Source_IP Target_Domain_Name
| sort _time
```

In this case, the `TargetDomainName` is `MicrosoftAccount`, which tells us that the account is a Microsoft Account rather than an Active Directory domain account. The event also shows `127.0.0.1` as the source IP, indicating that the authentication occurred locally on `Splunk_Lab`. This does not confirm that the five failed login attempts led to these four successful logins, but it also does not rule out that possibility.

So, at this point, the timestamps become important telemetry for determining whether the events may be related. The alert occurred at `2026-08-26 15:05:00`, while the underlying failed login attempts occurred between `2026-08-26 15:00:54` and `2026-08-26 15:01:16`.

The first successful login for `simplesmartcyber@gmail.com` occurred at `2026-08-26 15:02:09`, which was approximately 1 minute and 15 seconds after the first failed attempt and 53 seconds after the last failed attempt.

The close proximity makes it reasonable to investigate whether the successful login may be related to the preceding failed attempts. However, because the failed 4625 events did not record a target username or target SID, the available telemetry does not establish that the successful login was the result of those five failed attempts.
