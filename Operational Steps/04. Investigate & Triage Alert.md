#  Investigate & Triage Alert

### Process

As a SOC Analyst we want to follow a repeatable process while investigating this alert:
```text
✅ Alert triggered
     ↓
➡️ Initial documentation
     ↓
Validate the alert
     ↓
Establish scope
     ↓
Identify account + source
     ↓
Determine logon type
     ↓
Look for related activity
     ↓
Assess malicious vs. benign
     ↓
Determine severity/disposition
     ↓
Document findings
     ↓
Escalate or close
```

Our goal is to answer What happened, who/what was involved, how significant is it, and what should happen next?

This is where we shift our mind. Naturally, we know everything that just happened because we engineered the detection. However, we are switching hats and approaching this from the perspective that we are now a SOC analyst at work. One who has not seen this alert before. From that point of view, we now hold the responsibility of Investigating the legitimacy and severity of an unknown potential threat.

We want to reproduce the alert. This confirms that the alert wasn't a false trigger caused by the alert configuration. Modify the SPL to target the specific host mentioned in the alert:
```spl
index=* host="<WINDOWS-HOSTNAME>" "<EventID>4625</EventID>"
| bin _time span=5m
| stats count as failed_logins by _time host
| where failed_logins >= 5
```
In my case:
```spl
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| bin _time span=5m
| stats count as failed_logins by _time host
| where failed_logins >= 5
```
Make sure the date and time range covers the time the alert was triggered.

#### Targeted account

Determine which account was being targeted. Start with:
```spl
index=* host="<WINDOWS-HOSTNAME>" "<EventID>4625</EventID>"
| table _time TargetUserName TargetUserSid
| sort _time
```
in my case:
```
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| table _time TargetUserName TargetUserSid
| sort _time
```

#### Authentication source

Now determine where the authentication attempts originated. This is different from the host source. the host source tells us which machine generated the alert. the authentication source tells where the authentication attempt came from.

Use `ctrl` + `f` to search for `IpAddress`.

<img width="2472" height="1236" alt="image" src="https://github.com/user-attachments/assets/c65c6771-126b-466f-b446-a848350cbc36" />

<br>
<br>
<br>
<br>

The IP address is `127.0.0.1`. This is the local host address meaning the authentication attempt originated from the machine itself. This was not a remote login attempt from a different computer.

Just for reference a cleaner way to look for this would be to use:
```
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| rex field=_raw "Name='IpAddress'>(?<IpAddress>[^<]+)"
| table _time IpAddress
```

The rex field is is telling Splunk to Search the raw XML for Name='IpAddress'>, then capture everything until the next < and put it into a new field called IpAddress.

This is because Splunk is not automatically extracting a field called IpAddress. So we are essentially forcing it to do so.

- Authentication source: `local host`.

#### Logon type

Determine the Logon Type. This is one of the most important pieces of the investigation.

Common values include:

| Logon Type |	Meaning |
|---|---|
| 2	| Interactive	|
| 3	| Network	|
| 4	| Batch	|
| 5	| Service	|
| 7	| Unlock	|
| 8	| NetworkCleartext	|
| 9	| NewCredentials	|
| 10	| RemoteInteractive / RDP |
| 11	| CachedInteractive	|


```spl
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| rex field=_raw "Name='LogonType'>(?<Logon_Type>[^<]+)"
| table _time Logon_Type
```

#### Failure reason

Search for the failure reason

```spl
index=* host="Splunk_Lab" "<EventID>4625</EventID>"
| rex field=_raw "Name='FailureReason'>(?<Failure_Reason>[^<]+)"
| table _time Failure_Reason
```

We see `%%2304` for all 5 events. This is an index code that points to a text string within a local dll file. The associated text string is "An Error occurred during Logon". <br>
I know because I can access the effected host (my Windows VM) search for the event in Event Viewer, and open up the details that list the exact string along with the index code.

In the real world, a SOC would not likely have access to the multitude of endpoints that generate alerts on their dashboard. Neither would they have to rely on common knowldge to determine what the code means. <br>
They would most likely rely on SIEM field enrichment (the production standard). In an enterprise environment, raw logs are enriched before or during ingestion. The Splunk Add-on for Microsoft Windows (Splunk_TA_windows) automatically maps FailureReason codes like %%2304 to human-readable text via pre-built lookup tables. <br> 
However, that is not something we will explore in this lab for the sake of simplicity and focus. <br>
They may also rely on an internal knowledge base such as runbooks. SOC teams maintain internal documentation repositories (such as Confluence or internal SIEM wikis). Common codes like `%%2304` are documented in standardized triage playbooks so analysts can reference them instantly.

The point is, don't be confused by `%%2304`, or how to figure out what it means. just know that in our case it means "An Error occurred during Logon".

This is a very high-level message that doesn't give us much detail, but it is additional context.

We can conclude: 
Failure reason: An Error occurred during Logon
